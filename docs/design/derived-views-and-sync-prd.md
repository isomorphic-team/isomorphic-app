# PRD: Derived Views & Non-Destructive Sync

- Status: In implementation — §12 decisions resolved 2026-07-22; Phases 1+2 (FR-2 + all of FR-1) built 2026-07-22 and live; Phase 3 (FR-3 sync_records + resolve_import, FR-4 config) built 2026-07-23, verified by a real-GitHub E2E battery; remaining: reconciliation widget, contacts-brain ETL cutover
- Author: Jon Hansing (via Claude)
- Date: 2026-07-21
- Audience: the engineering session picking this up in `isomorphic-app`
- Related: `docs/design/org-roles-permissions.md`, `docs/design/brain-creation-and-init.md`, `CLAUDE.md` (Brain model, Content index)

## 1. Summary

Isomorphic supports free-form, interlinked markdown pages, but it has **no first-class
concept of _derived content_** — pages or sections whose value is a function of other pages
(directory listings, counts, rosters, "everything that links here"). Today the only way to
have such a view is to **materialize it as static markdown**, which is correct at write time
and drifts the instant any underlying page changes. Compounding this, the only way to
re-materialize at scale is an **external, destructive rebuild** that overwrites in-app edits.

This PRD asks for two capabilities that fix the problem at the root:

1. **Live derived views** — computed listings/counts/backlink collections, rendered fresh
   from the content index, never stored stale.
2. **Non-destructive bulk sync** — an import/upsert path that reconciles an external source
   into a brain without clobbering human edits, replacing the "wipe and regenerate" pattern.

## 2. Background & motivating use case

A real brain (`example-org/contacts-brain`) was seeded as a contacts knowledge base in the
Open Knowledge Format (OKF): ~2,900 **people** (`type: Contact`/`Reporter`), ~930
**organizations** (`type: Health System`/`Payer`/…), and ~20 **role** directories. People are
first-class pages linked to their organization; each org page carries a roster table and a
"N tracked contacts" count; `organizations/index.md`, `people/index.md`, and `roles/index.md`
are hand-enumerated listings. All of this was produced by an **external ETL script**
(`contacts-brain/scripts/build_okf.py`) from a spreadsheet.

`contacts-brain`'s `.isomorphic.json` is `{ "contentRoots": ["."], "sourceRoots": [], "logPath": "" }`
— i.e. the whole repo is editable content and no changelog is maintained.

The editorial team then began **curating in the app**: e.g. consolidating a duplicate
`Northwind Health` org — moving a contact onto the canonical page and deleting the duplicate.

What broke:

- The canonical org page still reads **"13 tracked contacts"** (should be 14). The count is
  plain text; nothing recomputes it.
- `organizations/index.md` still lists the deleted duplicate ("Advent Health – 1 contact").
  It is an ordinary content page to Isomorphic; nothing regenerates it.
- The only thing that _would_ regenerate those listings is re-running the ETL — which does
  `rmtree(people/, organizations/, roles/)` and rebuilds from the spreadsheet, i.e. it would
  **erase the consolidation**. So "wait for the next rebuild" is actively wrong.

### What the app does / does not do today (verified in source)

- **Auto-maintained on a page write** (`src/tools/librarian.ts`): `title`/`updated` plus any
  explicitly requested lifecycle `status` on the written page (other frontmatter keys preserved
  & merged); inbound-link
  repointing on move/rename; dangling-link flagging on delete; the changelog **only** if
  `logPath` is set. `isToolMaintained` (`src/lib/brain-config.ts`) protects **only** `logPath`.
- **No auto index, no entity types, no derived anything** (`CLAUDE.md` → "Brain model"):
  _"NO auto-generated by-type index. Only `wiki/log.md` is tool-maintained; `wiki/index.md` is
  now just a regular editable page."_
- **Content index** (`src/lib/brain-index.ts`, `src/db/index-schema.sql`): a derived D1 cache,
  reconciled to repo HEAD on every read (`ensureFresh`). `brain_pages(path,title,blob_sha,content)`
  and `brain_links(source,raw_target,kind,cnt)`; **links are resolved at query time** against
  the current page set. There is **no parsed-frontmatter storage** — you cannot currently query
  "pages where `frontmatter.organization = X`".

### Root cause

The product has one content primitive (the static page) doing two jobs: **authored content**
and **derived/aggregate views**. Derived views modeled as static pages are stale-by-construction,
and bulk regeneration of them is destructive-by-construction. Fixing individual counts or index
lines is whack-a-mole; the systematic fix is to make derived views _computed_ and bulk sync
_reconciling_.

## 3. Goals

- **G1.** A brain can express a view that is _computed from other pages_ (a listing, a count,
  a backlink collection, a group-by) and always reflects current content — no manual refresh.
- **G2.** Editing/moving/deleting a page keeps every derived view that references it correct,
  automatically (falls out of G1 if views are computed, not stored).
- **G3.** An external source (spreadsheet, CRM, another repo) can be (re)imported into a brain
  **without destroying human curation** — upsert/merge, not overwrite.
- **G4.** Works within the current architecture: stateless Worker, D1 derived index, GitHub as
  source of truth, read-time HEAD freshness (no new webhook dependency), OKF-compatible output.
- **G5.** Zero-migration for existing brains; existing static pages keep working.

## 4. Non-goals

- Not building a full query language or a spreadsheet/database product. A small, fixed set of
  view kinds (see FR-1) covers the use cases; resist a generic DSL in v1.
- Not reintroducing fixed entity types or a schema/taxonomy (explicitly removed 2026-07 per
  `CLAUDE.md`). Derived views operate on _frontmatter and links the brain already uses_, not
  on an app-imposed ontology.
- Not real-time collaboration, and not a webhook/event pipeline. Read-time freshness is the
  model; keep it.
- Not solving general two-way sync back to the external source (brain → spreadsheet). One
  direction (source → brain, reconciling) is in scope; the reverse is out.

## 5. Principles

- **P1. Derived data is computed, never stored.** If a value can be recomputed from other
  pages (a count, a listing), it must not be persisted as authored text that can drift.
- **P2. Human edits are sacred.** Any bulk operation must preserve in-app curation by default;
  destroying content requires explicit, visible intent.
- **P3. One source of truth per brain.** Make the source-of-truth policy explicit and enforce
  it; never let two writers silently fight (ETL vs app).
- **P4. Stay within the derived-cache model.** The GitHub repo remains authoritative; anything
  computed is reconciled against HEAD at read time, exactly like today's index.

## 6. Users & user stories

- **Curator (editorial team, non-technical).** "I consolidated two org pages in the app; the
  counts and the org index should just be right afterward, without me editing a 900-line file."
- **Brain author / operator.** "I want each org page to show its current contacts as a live
  list, and a directory of all orgs by sector, without hand-maintaining tables."
- **Data operator (owns the spreadsheet).** "When the spreadsheet gets 50 new contacts, I want
  to import them into the brain without wiping the consolidations the team did last month."
- **Agent (MCP client).** "I want to `find_inbound_links` / query pages by a frontmatter field
  so I can render or reason over aggregates."

## 7. Functional requirements

### FR-1 — Live derived views (read path) [P0]

A page (or a delimited region within a page) can declare a **computed view** that Isomorphic
renders from the content index at read/display time. Required view kinds for v1:

- **FR-1a Backlink listing** — "pages that link to this page," optionally filtered by the
  linking page's `type`/frontmatter. (This powers "contacts at this org" when contacts link to
  the org — data already present in `brain_links`.)
- **FR-1b Frontmatter-filtered listing** — "pages where `frontmatter.<key> [=|in] <value>`,"
  e.g. all `type: Health System` orgs, or all people with `organization = "HCA Healthcare"`.
  (Requires FR-2.)
- **FR-1c Count / aggregate** — the cardinality of any of the above (replaces "N tracked
  contacts"), and simple group-by counts (e.g. orgs per sector).
- **FR-1d Directory index** — child pages under a path prefix, optionally grouped by a
  frontmatter key, with per-item descriptions pulled from frontmatter (replaces the
  hand-enumerated `organizations/index.md` / `roles/index.md`).

Requirements:

- Views are **always current** relative to repo HEAD (reuse `ensureFresh`); a delete/move/add
  is reflected on the next read with no rebuild step (FR-1 satisfies G2).
- Views must be expressible in a way that **degrades gracefully as plain markdown** for
  consumers that don't execute them (OKF conformance, GitHub rendering). Prefer a fenced block
  or directive whose _fallback text_ is a static rendering, OR a mechanism where the computed
  result is surfaced in the app UI and via MCP read tools while the file stays valid markdown.
  (Design choice for implementers — see §8.)
- Available both in the **app UI** (`app/main.tsx` page render) and to **MCP read tools** so
  agents get the computed result, not the raw directive.
- Bounded cost: a view resolves in one or two D1 statements per the existing index design;
  respect `MAX_SCAN_PAGES`/subrequest budget and report truncation like today.

### FR-2 — Queryable frontmatter in the content index [P0, enabler for FR-1b/c/d]

Parse and store selected frontmatter keys per page in the D1 index so views can filter/group
by them.

- Extend the index (new table or columns, e.g. `brain_page_fields(brain_id, path, key, value)`)
  populated during (re)indexing in `src/lib/brain-index.ts`.
- Which keys to index: **all scalar and list-of-scalar keys by default, with hard caps**
  (decided 2026-07-22, see §12). A per-brain `indexedFields` allowlist in `.isomorphic.json`
  (e.g. `"indexedFields": ["type","organization","sector"]`) is an optional restriction,
  not required setup.
- Multi-value fields (YAML lists like `roles: [CEO, CFO]`) must be queryable element-wise.
- Reconciliation semantics identical to pages/links: incremental on changed blobs, HEAD-guarded.
- Back-compat: absent config → index a sensible default set or none; existing read tools unaffected.

### FR-3 — Non-destructive bulk ingest / sync (write path) [P0]

Replace the external "wipe-and-regenerate" pattern with a reconciling importer so an external
source can be (re)applied without destroying curation.

- **Upsert by stable key**, not by rewriting the tree. Given a batch of records each with a
  stable identity (e.g. email for a person, canonical name for an org), the importer must:
  create new pages, update changed fields on existing pages **without touching human-added
  content or unrelated frontmatter**, and **leave curated pages/edits intact**.
- **Field-level merge policy.** Distinguish _source-owned_ fields (safe to overwrite from the
  spreadsheet, e.g. `email`, `title`) from _human-owned_ content (never overwritten, e.g. body
  prose, notes, manual links, consolidations). Policy should be declarable, with a safe default
  (source updates scalar frontmatter it owns; never deletes human content).
- **Deletions are proposed, not automatic.** Records absent from the source must NOT auto-delete
  pages (a consolidation legitimately removes a page the source still lists). Surface a
  reconciliation report ("in source but not brain / in brain but not source / changed") for
  human decision; never silently destroy.
- **Runs through the existing write path** (bundle + PR/auto-merge per `writeMode`), so imports
  are reviewable and attributable like any other change, and respect branch protection.
- **Idempotent**: re-running with an unchanged source is a no-op (no churn, no spurious commits).
- Identity/dedup and normalization (the union-find, org-alias collapsing in the current ETL)
  should live on the **source side** or in a documented pre-processing contract; the app-side
  importer consumes already-keyed records. (Design choice — see §8/Open Questions.)

### FR-4 — Source-of-truth policy [P1]

Make the ETL-vs-app tension explicit rather than implicit.

- A brain (or a path subtree) declares whether it is **app-authored** (curation wins; imports
  reconcile) or **source-authored** (external source wins; app edits are advisory). Default:
  app-authored, given P2.
- The importer honors this policy (FR-3 merge behavior derives from it).

### FR-5 — Migration & back-compat [P1]

- Existing brains with static index pages and baked counts must keep rendering unchanged until
  intentionally migrated.
- Provide a path to convert a static listing/count into the equivalent computed view (FR-1),
  and guidance/tooling to strip now-derived values (e.g. remove "N tracked contacts" text).
- No breaking change to `.isomorphic.json` (new keys optional, defaults preserve today's behavior).

## 8. Proposed approach (design sketch — not binding)

Grounded in the current architecture; implementers choose specifics.

- **Views as directives with static fallback.** Represent a computed view as a fenced block,
  e.g.:
  ```okf-view
  kind: backlinks
  filter: { type: Contact }
  as: table
  columns: [title, roles, email]
  ```
  The app and MCP read tools execute it against the index; the file remains valid markdown.
  **Decided (2026-07-22): fenced blocks, WITH a cached static rendering** kept beneath the fence
  (inside marked delimiters) so non-executing consumers (GitHub, raw OKF) see a real table.
  The cached rendering is cosmetic fallback only: app + MCP always compute live and ignore it;
  it refreshes whenever its own page is written through our tools and is allowed to go stale
  between writes (edits to OTHER pages do not touch it). A cheap "refresh snapshots" act or
  opportunistic refresh-on-save is a possible follow-up, not v1. Alternative considered: a
  dedicated `type: view` page. Tradeoff: fenced blocks compose inside authored pages (org page
  can have prose + a live roster); dedicated view pages are simpler but less flexible.
- **Frontmatter index (FR-2)** as an additive D1 table populated in the same
  incremental-reindex pass that already fills `brain_pages`/`brain_links`. Resolution/query at
  read time mirrors `loadResolvedGraph` for links. Ships via the wrangler migrations framework
  (`migrations/`), additive/backward-compatible per `CLAUDE.md`.
- **Importer (FR-3)** as an MCP tool (e.g. `sync_records` / `import_bundle`) taking keyed
  records + a merge policy, computing a diff against current pages (read via the index to
  _discover_ which pages to touch, then fetch those blobs fresh — the existing
  read-modify-write pattern used by `move_page`), and emitting one write bundle
  (PR/auto-merge). Reuses link-repointing so merges under a canonical page keep links intact.
- **Freshness** everywhere via the existing read-time HEAD guard — no webhook (consistent with
  the documented decision in `CLAUDE.md`).

## 9. Constraints / architectural context (must respect)

- Stateless Cloudflare Worker; **no `node:*`** in `src/lib/` or `worker.ts`.
- D1 is the only derived store; GitHub repo is the source of truth; index is a cache reconciled
  at read (`ensureFresh`), never authoritative.
- Worker subrequest budget; batched GraphQL `fetchPages`; `MAX_SCAN_PAGES` (1500) sanity bound;
  report truncation.
- Writes land per `writeMode` (direct vs PR + auto-merge) from `.isomorphic.json` / branch
  protection; imports must not bypass this.
- Output must stay OKF-valid and render acceptably on github.com (graceful degradation, FR-1).
- Multi-tenant: everything keyed by `brainId`; no cross-brain leakage.

## 10. Acceptance criteria

- **AC-1 (FR-1/2):** On `contacts-brain`, an org page renders its current contacts as a live list and
  a live count. Deleting a contact page or moving a contact to another org changes both on the
  next read, with **no** external rebuild and **no** manual edit.
- **AC-2 (FR-1d):** `organizations/index.md` (or its replacement) lists exactly the org pages
  that currently exist, grouped by sector, with no stale/deleted entries — recomputed, not
  hand-maintained.
- **AC-3 (FR-3):** Re-importing the source spreadsheet after the Northwind Health consolidation
  **preserves** the consolidation (duplicate stays gone, contact stays moved), applies genuinely
  new source rows, and produces a reviewable reconciliation report. Re-import with an unchanged
  source yields no commit.
- **AC-4 (regression):** Existing brains with static pages and counts render unchanged; no
  `.isomorphic.json` change required for them.
- **AC-5 (perf):** A derived view and a frontmatter query each resolve within the existing
  index budget (one or two D1 statements; within subrequest limits) on a ~4,000-page brain.

## 11. Phasing

- **Phase 1 (P0):** FR-2 (frontmatter index) + FR-1a/1c (backlink listing + count). Unblocks
  the highest-value contacts-brain fix (live org rosters + counts) with data mostly already present.
- **Phase 2 (P0):** FR-1b/1d (frontmatter-filtered listings + computed directory indexes).
  Replace the static `*/index.md` files.
- **Phase 3 (P0):** FR-3 non-destructive importer + FR-4 source-of-truth policy. Retire the
  destructive ETL rebuild.
- **Phase 4 (P1):** FR-5 migration tooling (convert static listings → views; strip baked counts)
  and docs.

## 12. Design decisions (resolved 2026-07-22)

Formerly open questions; resolved with Jon before implementation started.

- **Directive syntax & fallback: fenced `okf-view` block + cached static rendering.**
  GitHub/raw-OKF must show a real table, at the accepted cost of that stored rendering being
  stale between writes. The cached copy lives beneath the fence inside marked delimiters, is
  ignored by all executing consumers (app + MCP compute live from the index), and refreshes
  only when its own page is written through our tools. See §8 for mechanics.
- **Frontmatter indexing scope: all scalar and list-of-scalar keys by default, with hard caps**
  (order of ~24 keys/page, ~256-char values, list elements indexed element-wise up to a small
  bound). Zero-config: any brain's frontmatter is queryable day one. `indexedFields` in
  `.isomorphic.json` becomes an OPTIONAL override/restriction for pathological brains, not
  required setup. Type coercion: store the raw string plus a numeric column populated when the
  value parses as a number (so `rank` sorts numerically); booleans stay strings.
- **Importer contract: identity/dedup/normalization is a source-side responsibility**, per a
  documented pre-processing contract. The app importer consumes already-keyed records
  (`{key, fields, body?}`) and stays simple. The current ETL's union-find + alias collapsing
  stays where it is.
- **Merge policy expression: declared per-import call, with a safe hardcoded default** (the
  source may update only the scalar frontmatter keys it explicitly lists as source-owned; it
  never touches body prose and never deletes pages). Per-brain policy arrives with FR-4 and
  layers on top; per-field frontmatter markers rejected (magical, hard to debug).
- **On-demand snapshots: deferred.** The cached fallback rendering above already covers the
  GitHub-rendering need; a dated, explicit export/archive snapshot act can come later if a
  use case appears.

## 13. Out of scope (v1)

- Two-way sync (brain → external source).
- A general query DSL or user-defined joins beyond the fixed view kinds in FR-1.
- Webhooks / push-based freshness.
- Access-control changes (covered by `org-roles-permissions.md`).

## 14. Appendix — the contacts-brain fix as a consumer

Once FR-1/2 land, `build_okf.py` should stop baking derived data: drop the "N tracked contacts"
counts and the hand-enumerated `*/index.md` listings, emitting computed views instead. Once FR-3
lands, the ETL's `rmtree`-and-regenerate becomes a reconciling import. This turns contacts-brain from a
"seed once, never re-run safely" artifact into a continuously curatable, re-syncable brain — the
holistic fix this PRD targets.
